# 一株自有识别模型与微调路线

后续进展（2026-09-22）：已生成 1,000 种候选清单，完成 3 类/90 张公开授权图片的
真实分类头训练冒烟；完整清单采集/训练任务已启动但尚未完成。
见 `china-common-plants-training.md`。下文保留 9 月 21 日可行性评估的历史范围。

日期：2026-09-21。用户要求评估自有模型／微调方向。
这是下一阶段的可行性评估，**未使用真实植物数据训练模型、未使用私人照片、未租用 GPU**。
已补充本机合成向量分类头性能测试；没有导出或部署该合成测试的权重。

## 本机实测后的可行性结论

硬件实际读取：Xeon E3-1225 V2，4 核、约 7.6 GiB 内存；
PCI 枚举中是 Intel 集成显卡，当前 PyTorch 为 `2.14.0+cpu`，
`torch.version.cuda=null`、`cuda.is_available=false`，当前环境没有可用 CUDA 加速。
这不等于“只要换成 CUDA wheel 就会有可用 GPU”。

### 小分类头：算力可行，真实数据尚未就绪

使用 5,000 条 **随机合成** 768 维向量、随机对应的均衡类别，
单 CPU 线程、batch=256、AdamW、10 轮共 200 步：

| 类别 | 分类头参数 | 分类头 FP32 权重大小 | 10 轮训练耗时 | 进程峰值 RSS |
| --- | ---: | ---: | ---: | ---: |
| 50 | 38,450 | 153,800 bytes | 0.7954 秒 | 323.43 MiB |
| 200 | 153,800 | 615,200 bytes | 1.9606 秒 | 325.55 MiB |

每个规模只做了一次资源试验，不是长期重复的性能基准。
这验证了“已取得固定特征后，训练小分类头”的计算规模在本机可承受，
**不包含图片下载、审核、特征提取、超参搜索，也没有测量植物准确率**。
峰值 RSS 是整个 Python／PyTorch 进程的累计峰值，不只是分类头占用。
标签与特征没有植物语义，不能根据训练损失推断真实识别收益。

当前经项目来源文档确认的随包照片只有两张银杏示例，
不足以建立多类训练／独立验证集；没有查看私人照片来补充这个数量。
所以现阶段的首要缺口是授权明确、标签可靠、覆盖目标场景的图像数据，
不是分类头的 GPU 预算。

### 全量微调：不适合与现有服务共用这台机器

仅读取已有 BioCLIP 2 safetensors 头部，得到：

- 全部状态张量约 4.276 亿元素，视觉部分约 3.040 亿元素。
- 粗估 FP32 权重 + 梯度 + Adam 两份动量状态：全模型约 **6.372 GiB**。
- 若只训练视觉部分、仍保留其他权重，按同样假设约 **4.990 GiB**。

这是按张量元素数的规划估算，不是实际训练峰值；状态中可能含非训练张量。
数字**尚未计入激活、工作区、框架开销、数据缓冲和线上服务**。
因此不建议本机一边运行现有服务一边做全量微调；减少精度或参数、
采用适配器也需要具体测量，不能直接把理论节省当作已验证可运行。

### LoRA／局部微调：有条件可行，不能直接套脚本

实际模型中有 24 组视觉 `attn.in_proj_weight`，形状为 `[3072,1024]`，
以及 24 组输出投影 `[1024,1024]`。
假设两类投影都加入 rank=8 的低秩适配器，参数量约 1,179,648，
FP32 参数／梯度／两份动量状态合计约 18 MiB。

这个估算**不包含冻结骨干与激活**，没有在完整 BioCLIP 上实现或运行 LoRA。
当前 Q/K/V 是合并参数，并非通常脚本里的独立 `q_proj`／`v_proj` 线性层。

已另做一个最小技术试验：在 `torch.nn.MultiheadAttention(16,4)` 上，用原生
`parametrize.register_parametrization` 给合并 QKV 和输出投影加入 rank=2 适配器。
实际验证零增量时输出一致、适配器能获得梯度、一步更新改变前向结果、
基础权重保持不变。这说明这种参数接线方向有可行性，
**不是完整 BioCLIP、rank=8 大模型训练或真实植物数据的验收**。
该试验只用随机张量，没有保存训练权重。

不能只看到“可训练参数数”就认为整个模型接线正确。
先完成冻结特征基线和真实数据评测，再做小批次适配器实验，必要时另行确认 GPU 预算。

实测和估算原始数据：`model-feasibility-20260921.json`。
这次只做 CPU 合成资源试验和公开模型头部分析，没有访问、训练或上传私人图片。

## 结论：先做自己的数据与识别分支，不从零训练视觉骨干

建议按成本与可验证性递进：

| 阶段 | 实际做什么 | 主要前提 |
| --- | --- | --- |
| A：图像参考库 | 冻结现有编码器，用带标签参考图的向量做检索／原型匹配 | 有可靠图片及标签，无须训练骨干 |
| B：分类头 | 冻结编码器，只训练小型分类头 | 每个目标类别有足够且多样的训练／验证图 |
| C：有限微调 | 解冻少数视觉层，或验证适配器方案后训练 | A/B 的独立测试确有瓶颈且数据质量过关 |
| D：大范围微调或从零训练 | 改造整个视觉模型 | 大规模、多样化数据与额外算力；不是当前优先项 |

“预训练模型 + 自己的数据、分类头、索引、拒识规则和版本管理”
就是有实际产品价值的自有识别方案，不必从零训练才算自己的模型。

PyTorch 官方迁移学习教程区分了固定特征提取器与微调预训练模型两种方式。[S1]
BioCLIP 2 官方模型卡提供零样本／少样本评测并标明模型许可 MIT；
这支持将其作为候选骨干，但不能推导出它在一株图片上的微调收益。[S2]
DINOv2 官方也提供 k-NN 与线性评估入口，可作为冻结特征方案的对照。[S3]

## 一、首先缺的是图像数据，不是中文名称

19,716 个可见物种是名称／分类目录，不等于有 19,716 类的训练图片。
不能用中文名、百科文字或模型自己的猜测直接替代可靠视觉标签。

建议第一批只选 **30–50 个有实际需求的物种**：

- 优先中国常见观赏植物与已经有可信错例的种类；
- 同时包括真正易混淆的近缘种，不只挑外观截然不同、容易得到高分的类别；
- 每种先规划 30–100 张可用图片，来自不同个体、观察、背景和花／叶／整株视角；
- 另准备非植物、库外植物、无法可靠判到种级的照片。

这些数量是个人项目试验规模的建议，不是保证训练成功的数据门槛。
第一批类别由可取得的数据和实际问题决定，不承诺一轮覆盖整个目录。
PlantCLEF 的地域性训练数据也不能直接补齐此次缺少的桂花、银杏等全部目标。

## 二、数据最小规范

先用一个离线图片目录和 JSONL manifest，不新建标注平台或数据微服务。
建议记录：

```text
sampleId / speciesId / scientificName / labelRank / labelSource / reviewStatus
sourceUrl / author / license / permittedUse / acquiredAt
imageSha256 / duplicateGroup / individualGroup / observationGroup
organ / captureConditions / split / datasetVersion
```

- `speciesId` 对齐现有稳定物种 ID；个体分组标识与物种 ID 分开。
- 图片哈希只用于重复文件检查，不能代替 Plant 个体 ID。
- 明确分配训练、调参、最终测试集合，再生成裁剪；同一照片的变体不能跨集合。
- 同株、同次观察和近重复照片必须整体分组，避免模型记住背景后形成虚高分数。
- 稀有类别、不同地点／季节、叶片与花朵分别报告效果，不能只给整体平均数。
- 只能确认到属的图片保留属级标签或排除种级监督，不能硬塞进某个种。
- 用户点击“确认”是反馈，不自动当作经过专家核实的金标准；
  测试标签需要更严格核对，模型预测不能给自己的测试集充当答案。

### 授权边界

先使用来源和许可清晰、允许预期用途的公开资料或用户明确授权的数据。
模型权重许可不代表训练图片都能复制；逐图保留来源、作者和适用条款。
私人株记照片默认不进入训练、评测或参考图库；也不能因用户授权识别，
就推定其同意模型训练。公共标注文件不保存私人图片链接、账号或精确地点。

如以后接入用户贡献，先明确贡献与撤回流程。删除原图片不等于能自动消除已训练权重
中的影响，不能做这样的产品承诺。第一批试验不依赖私人数据，降低这些复杂度。

## 三、阶段 A：先建立图像召回分支

复用当前 BioCLIP 图像编码器，离线计算审核通过的参考图片特征。
每个物种可保留多个实际参考向量，或按花／叶／整株分组建立原型，
不要把不同观察条件粗暴平均成唯一“标准照片”。

识别时：

```text
输入图及局部 → 同版本编码器
             ├─ 现有物种文本向量召回
             └─ 自有参考图片向量召回
                      ↓ 去重、融合
                  现有重排与人工确认
```

这一步不更新模型权重，便于定位问题：如果加入可信参考图就有帮助，
可先改善召回，不必马上承担微调成本。
是否改善仍须留出的独立图片测试，不能用参考图库中的照片自测命中率。
不同模型的向量空间不能直接混用；所有索引都要绑定编码器和预处理版本。

## 四、阶段 B：冻结骨干，训练自己的分类头

把特征离线提取后，在这些向量上训练线性层／小型分类头，
先用已有 PyTorch 环境即可，不另建训练平台或先升级依赖。[S1]

- 输出类别映射到现有物种 ID，类别表与权重一起固定版本。
- 调整类别采样或损失权重来处理样本不均衡；保留未加权基线对照。
- 训练集拟合分类头，验证集决定正则化、停止时机和拒识门槛；
  最终测试集不用于反复挑参数。
- 先与阶段 A 的图像检索，以及现有 BioCLIP 的同一批测试图比较。
- 分类头只覆盖第一批类别，不能让它对所有植物强制给出这几十类中的一个。
  继续保留广覆盖 BioCLIP 分支和“不确定”路径。

因此第一版自有模型可以是一个很小的专用识别头，而不是另一个巨大的模型权重。
CPU 是否足够完成具体训练、训练多久，需在实际数据规模下测量，不作时长承诺。

## 五、阶段 C：数据支持后再微调骨干

只有冻结特征／分类头仍存在一致、可复现的错误时，才增加微调自由度。
先考虑末端少量视觉层和分类头，再评估 LoRA 等适配器。
**已检查本地 open_clip 的合并注意力参数并完成最小 PyTorch 参数化试验，
但还未完成完整 BioCLIP 与具体 LoRA 训练实现的接线验收，
不能把 LLM 的适配器脚本直接套用。**

对 BioCLIP 还需注意：

- 只训练图像分类目标可能改变原本图文对齐；不能默认原零样本能力完全保留。
- 修改编码器后重新计算对应图片索引；更新文本侧则同步重建文本索引。
  不能将新旧版本的向量随意混在一起。
- 保留原模型作为广覆盖分支和蒸馏／回归对照，不因少数目标种提高就整体覆盖。
- 采用较小的训练范围与验证集早停，检查近缘种、库外样本、模糊图及非植物是否退步。
- 单独保存微调权重／适配器与完整训练配置，不能覆盖已发布的基础权重。

完整训练的 GPU 型号、显存和预算须在小批次测量后确定；
当前约 8 GiB CPU 主机优先承担离线特征或小分类头试验，不假定它适合全量微调。
开通任何收费算力前先确认预算，不在本轮执行。

## 六、验收和部署

一个可发布版本至少同时保存：

- 基础模型来源、revision、许可及权重校验值；
- 数据集 manifest 版本、划分规则与标签审核状态；
- 类别 ID 映射、预处理、训练配置、随机种子及软件版本；
- 验证集确定的拒识／校准参数，以及未用于选模型的测试结果；
- Top-1、Top-5、每种效果、接受覆盖率、库外／非植物误判、延迟和内存；
- 与旧方案逐图对照的改善与退步，不只挑成功案例。

阈值须来自独立验证，不把 softmax、余弦相似度或多模型一致直接称为正确概率。
公共评测报告不包含私人照片、链接或账号。

通过后注册为新的服务端 solution，保持前端协议、物种 ID 和旧记录不变，
不改写原始识别结果。先显式试用、可回滚，再考虑替代某个阶段。
目前没有训练产物或可宣称的新准确率。

## 七、建议的下一项实际工作

先确定第一批物种和图片来源，制作小型、可复核的公开图片集及独立测试集，
然后运行 **同一编码器：文本召回 vs 图片召回 vs 线性分类头** 三组对照。
这比现在直接从零训练或下载更大的模型，更容易确认问题在哪里。

当前两级工程方案仍按 `../recognition-cascade.md` 继续；训练不是未完成权重安装
的替代证明，也不会在没有数据的情况下自动开始。
