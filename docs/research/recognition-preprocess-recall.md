**没有切换线上模型、运行新的识别实验或测得新的准确率**。

后续实现状态：已注册 `bioclip-multiview-plantclef` 并接通两级流程、
缓存和离线入口，见 `../recognition-cascade.md`。正式 PlantCLEF 包下载／校验及

## 已确认的兜底范围

2026-09-21，用户取消第三层 LLM／Jev 兜底。后续只实现本地两级方案：

```text
照片质量检查
  → 第一级：预处理 + 多视图召回 + BioCLIP v2 重排
  → 仍不确定：第二级 PlantCLEF 辅助识别
  → 仍无可靠候选：返回待确认，保留手动选择、重拍和建档路径
```

- 不接入第三层文字／视觉大模型，不预留外发私人照片的自动兜底调用。
- 严重低质量或明确非植物不强行逐级分类；服务异常与识别不确定分别处理。
- 升级及接受门槛须通过验证集确定，不能将相似度、softmax 或模型自述当作正确率。
- PlantCLEF 保留类别覆盖和库外拒识限制；只返回能映射到现有物种 ID 的候选，
  不以猜测名称新建物种，也不覆盖前一级原始结果。
- 本节是确认后的实现方向，不是上线记录。代码现已提供两级实验方案，
  但正式模型资产与真实效果仍待验证；原有三个 BioCLIP 方案均保留。

## 结论

建议下一项方案命名为 `bioclip-multiview-recall`：

```text
同一张照片
  ├─ 现有整图预处理 → BioCLIP v1 → Top 50，完整保留
  ├─ 局部视图 A     → 同一个 v1 → Top 50
  └─ 局部视图 B     → 同一个 v1 → Top 50
        ↓ 按物种 ID 去重，融合局部排名，最多增加 50 个新候选
     ≤100 个候选 → 现有 BioCLIP v2 重排 → 原有识别结果接口
```

优先改变“模型看到了什么”和“哪些候选进入重排”，不先换更大权重、
训练新模型或接外部识别 API。仅修改服务端，原方案保留为对照与回滚项。
名称是拟议的新注册项，**当前代码尚未提供该 solution ID**。

## 一、现有流程的实际瓶颈

本轮读取 `catalog_recognition.py`、`recognition_rerank.py`、
`recognition_solutions.py`、`journal_store.py`、`recognition.py` 及本地已安装库。

1. **已有基础清理，不应重复包装成新算法。**
   `read_photo` 已做方向校正、RGB 转换和 EXIF 移除；上传保存前缩至最长边
   1600 像素并以 JPEG quality=85 编码。输入格式／像素数限制也已存在。
2. **v1 当前只有一个整图视图。**
   `preprocess_img` 把图像直接变为 224×224。它保留全图范围，但非方形照片会改变比例；
   图片里很小的叶片或花朵在这个输入尺寸中也可能缺少细节。
   这与已核查的 pybioclip 官方实现一致，不应未经对照就称它是实现错误。[S1]
3. **v2 只重排 v1 前 50 个候选。**
   正确物种不在候选池时，重排无法补回。当前在线最多对外返回 5 个候选，
   `BioClipReranker` 已允许至多 100 个候选，便于开展扩池实验。
4. **v2 当前重排仍使用原照片的默认中心裁剪。**
   局部视图解决召回遗漏，不自动解决重排看不见关键部位的问题；
   OpenCLIP 提供不同缩放／裁剪模式，必须固定版本和处理方式做对照。[S2]
5. **不能把所有错误归咎于召回。**
   既有诊断记录中，一个人工确认候选在 v1 是第 19 名，进入了前 50；
   v2 重排后第 5 名，仍不是第 1。这个案例属于“候选已召回但首选仍错”，
   扩池不保证解决。这里只引用已有匿名汇总，没有重新查看私人照片。
6. **可见性与视觉识别要分开评估。**
   模型检索仍包含完整植物参考，并有全生物类别的非植物反证。
   19,716 个可见物种不等于模型只有这些类别。现在的输出先截取前 5，
   `JournalStore.finish` 再去掉隐藏项；候选变少可能是显示过滤，不是召回失败。

本轮只读取两张已有公开示例的尺寸：1000×750、900×675，均为 4:3。
在理想中心正方形裁剪中，仅保留原图面积的 75%；这是几何计算，
**不是证明被裁掉的 25% 含有植物特征，也不是准确率测量**。

## 二、预处理方案

### 保留基线，另外增加视图

不要直接替换原整图分支，否则可能修好一类照片却丢掉另一类。
所有视图由同一张已校正方向的 RGB 照片生成，在缩至模型尺寸之前裁剪。

| 分支 | 首轮建议 | 用途与限制 |
| --- | --- | --- |
| V0 | 完全保留当前整图处理 | 作为可重复基线，确保原召回候选不丢 |
| V1/V2 | 两个有重叠的方形局部 | 放大局部；不是检测器，不能宣称已定位叶片或花朵 |
| 对照项 | 等比例缩放后补边的整图 | 检查比例失真影响；补边同样可能改变模型输入分布 |

可复现的局部初始配置：边长为短边的 0.8 倍，沿长轴的 1/3、2/3 处取中心，
短轴居中并将框限制在图内；正方形照片默认沿横轴。相同／过小裁剪去重或跳过。
**这些是拟议初始参数，不是论文证明的最佳参数。**
它不能覆盖所有偏角主体，所以 V0 不能删除；先比较收益，再决定是否需要更多位置。

首版每张图最多 3 路 v1 推理、仍为 1 路 v2 图像推理。
“整图补边”先作为独立消融项，不与所有裁剪组合一口气叠加。

### 暂不加入

- 不靠“绿色像素”裁主体：花、枯叶、树皮不一定是绿色，背景也可能是植物。
- 不做生成式修复、超分辨率补细节、强锐化／改色，不制造鉴定特征。
- 不先引入分割大模型或新 GPU 服务；分割错误也可能去掉有用部位。
- 不用地点硬过滤或默认索取 GPS，不把多视图误当成多张独立证据。

### 外部证据的适用边界

PlantCLEF 2025 的一项公开方案使用图像分块、patch 预测及融合，
说明局部视图是值得比较的植物识别方向。[S3]
但它针对多物种样方照片，使用另一套模型和输入分辨率；
不能把其成绩当作一株的单株手机照片正确率，也不直接照搬其地理先验或 4×4 分块开销。

## 三、召回与合并

### 先保护原前 50，再补充局部候选

令 `A` 为现有整图的前 50 个唯一物种 ID。
从 V1/V2 各取前 50，排除已在 `A` 中的物种，对剩余候选融合排名并最多补入 50：

```text
final_pool = A ∪ top_50(fuse(V1, V2) − A)
```

去重只按稳定 `speciesId`，不能按中文别名、属名或照片哈希。
同时保存候选来自哪个视图、各路排名、裁剪框和原始相似度。
这是拟议内部审计数据，不是现有外部 API 的已实现字段。

**集合层面可以保证：原前 50 包含于新候选池。**
在标签与名录固定的条件下，新池的召回覆盖不会少于原池；
但这不保证最终 Top-1 上升，因为新增候选也会带来干扰。

### 融合建议：RRF

局部新候选采用 Reciprocal Rank Fusion 作为简单基线：

```text
fusion_score(species) = Σ 1 / (k + rank_in_view)
```

缺席的视图不贡献分数；先用 `k=60` 做可复现起点，同分按物种 ID 稳定排序。
RRF 原始研究是信息检索排名融合，不能把其改进幅度套用到植物识别。[S4]
这里选它是为了避免把不同视图下的相似度当成同一尺度的正确概率；
最终仍保留各路原始分数。融合分数与 v2 相似度都不是可信概率。

### 不以牺牲拒识换取“命中率”

- 保留整图的非植物反证与现有低细节拒识；局部裁到一片背景叶子不能自动覆盖整图拒识。
- 多个视图冲突只是诊断信号，不能据此断言有几种植物，也不能强制给出单一正确种名。
- 不先把召回范围硬缩成可见中文物种，否则库外／缺名植物可能被硬配到另一个可见种。
- 可见性过滤的输出补足另做一项实验：从完整重排结果选可见候选，但始终保留
  原始首选及隐藏首选的不确定状态；不把可见候选提为“已经识别正确”。

## 四、如何判断有没有改善

至少区分三个环节，不能只看最终页面有没有出现一个熟悉的中文名：

| 指标 | 回答的问题 |
| --- | --- |
| 原始 Top-50 命中 vs 新池 Top-100 命中 | 正确种是否进入重排池 |
| 相同容量下单图 Top-100 vs 多视图 Top-100 | 改善是视图贡献，还是仅扩大 K |
| 最终 Top-1、Top-5 | v2 是否真的把正确种排上来 |
| 接受覆盖率、已接受结果的错误率、负例误判 | 是否只是放松“不确定”门槛 |
| 冷／热耗时、P95、峰值内存和排队时间 | 当前机器是否承担得起 |

先准备约 50–100 张有可靠标签的植物照片及单独的非植物负例，
包含花、叶、远景、小主体、偏角、近缘种和明确无法判种的照片。
同一照片的所有裁剪、同一植株的近重复照片不能分散到调参集与验证集。
参数固定后再看留出的验证样本；小样本报告命中数与分母，不宣称通用准确率。
无法确认种级标签或多主体照片单列，不强行给它们唯一“标准答案”。

保持同一物种库、同一图片和同一标签，比较：

1. 当前 v1 Top-50 + v2；
2. 单图 v1 Top-100 + v2；
3. 保留原整图 + 等比例整图召回对照；
4. 整图 + 两个局部召回、保护原前 50 + v2。

若正确种已在池中而最终排名仍错，应把问题转交重排阶段；
不能靠无限增加候选或对某一张已知答案的照片手调裁剪框。
后续才比较 v2 多视图或图像原型检索，不在首轮同时改变所有环节。

## 五、成本与实施范围

本轮实际观察：4 个可用 CPU，内存总量 7.6 GiB、available 约 2.9 GiB，
swap 已用约 2.6 GiB。资源快照不能推断是哪一个进程造成，也不能据此保证并发能力。

- 复用已加载的 v1/v2，顺序处理视图，不额外加载模型副本。
- 新候选最多 100，保持单 worker；不要直接改成无上限召回。
- 当前 v2 只有 1024 项内存文本缓存。以往对照的首次文本编码约 57 秒是旧实验结果，
  不是本轮新测量；多视图带来的新候选可能再次触发此成本。
- 上线前应加入版本化磁盘文本缓存或离线预热：缓存键包含权重、tokenizer、
  模板版本和学名。缓存只保存公共标签向量，不保存用户照片。
  它改善时延，不应包装成准确率提升。
- 裁剪在内存生成，不新增私人照片副本，不发外部 API，不在日志记录私人图片链接。

预期代码落点（尚未改动）：

- `catalog_recognition.py`：多视图召回及可复用的特征检索；
- 小型预处理／融合模块：确定性裁剪、去重、RRF；
- `recognition_solutions.py`：增加独立方案 ID，保留旧配置；
- `recognition_rerank.py`：复用现有 ≤100 候选接口，补充文本缓存；
- 既有离线入口和测试：验证候选保留、去重、拒识、上限及缓存版本。

不改客户端、数据库名称或历史识别，不重训练、不新建微服务。
只有在独立样本上看到最终质量改善、且资源开销可接受后，才显式切换线上方案。
